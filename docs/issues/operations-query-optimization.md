# 운영 월별 사용량 쿼리 최적화

운영 카탈로그의 `OPS_ANALYSIS_002`와 `OPS_ANALYSIS_005`는 카테고리별 월 사용량을
고객·월 단위로 합산한 뒤 통계를 계산합니다. 기존 방식은 상세 카테고리 행을 차원과 조인하고
가명 고객 문자열로 집계해, 기간이 길어질수록 조인 입력과 집계 비용이 커졌습니다.

## 원래 SQL과 최종 SQL의 차이

| 단계 | 원래 방식 | 최종 방식 |
| --- | --- | --- |
| 기간 제한 | 날짜 차원의 `calendar_month` | fact의 그룹 키 `month_key` |
| 고객·월 합산 | 차원 조인 후 `analysis_user_key`, `calendar_month`로 집계 | 차원 조인 전에 숫자 `customer_key`, `month_key`로 집계 |
| 차원 조인 입력 | 고객·월·카테고리 행 | 고객·월 합계 행 |
| 카테고리 차원 | 카테고리 표시 차원까지 조인 | 모든 카테고리 합계이므로 표시 차원 조인 생략 |
| 월별 통계 | 평균·중앙값, 분포·집중도 | 같은 계산·빈 월 처리·반올림·출력 순서 유지 |

[130 스키마 파일](../../db/schema/130_install_operations_monthly_preagg_view.sql)은
`ai_operations.v_customer_monthly_usage_filtered_preagg` 일반 뷰를 정의합니다.
뷰는 숫자 고객·월 키로 사용량을 합산한 뒤 고객·날짜 차원을 조인하고 기간 제한용 월 키를 노출합니다.
원본 숫자 고객 키는 외부에 공개하지 않습니다. 별도 저장 데이터와 REFRESH 작업은 없습니다.
월 키는 월 첫날 YYYYMMDD이며, 고객 키와 가명 키의 일대일 대응과 유효한 카테고리 FK가 전제입니다.

운영 카탈로그 002·005는 이 뷰와 월 키 필터를 사용합니다.
전체·초기화·증분/정정 파이프라인은 130을 적용하고, Lambda도 같은 SQL 경로를 사용합니다.
Lambda 반영에는 새 이미지 재배포가 필요하며 외부 n8n의 등록 카탈로그·SQL도 갱신해야 합니다.
원래 SQL은 비교 기준으로 `tools/query-plans/ops_analysis_002.sql`, `005.sql`에 보존합니다.

## 실행계획에서 확인한 변화

기존에 사용자가 제공한 postgres 계정의 002·6개월 실제 계획에서
고객 차원 조인에 전달되는 fact 측 입력은 775,892행에서 고객·월 합계 59,684행으로 줄었습니다.
기존 계획은 fact 전체 1,665,248행을 스캔해 날짜 차원과 조인했고,
최종 계획은 fact의 월 키 필터 후 숫자 키로 합산했습니다.
이 계획 자료는 아래 운영 계정의 시간 측정과 별도 실행 자료입니다.
계획 노드의 cost를 ms로 해석하거나 두 실행 자료를 한 측정으로 합치지 않습니다.

메모리만 4MB에서 64MB로 늘린 이전 비교도 있었습니다.
그 결과와 이번 SQL·뷰 변경의 효과는 구분합니다. 아래 전후 비교는 양쪽 모두 64MB입니다.

## 운영 계정에서 측정한 결과

다음은 기존 사용자 제공 로그의 기록입니다. 이번 파일 정리 중 운영 DB를 다시 측정한 값은 아닙니다.
PostgreSQL 18.3의 `n8n_operations` 직접 로그인, 같은 repeatable read 읽기 전용 스냅샷,
`work_mem=64MB`, `force_custom_plan`, `jit=off`, 문장 제한 30초에서 측정했습니다.
각 쿼리·기간·방식을 한 번 워밍업하고 교대로 5회 실행한 중앙값입니다.

| 쿼리 | 기간 | 원래 중앙값 ms | 최종 중앙값 ms | 시간 감소율 |
| --- | --- | ---: | ---: | ---: |
| 002 | 1개월 | 345.139 | 155.422 | 54.97% |
| 002 | 6개월 | 1231.185 | 689.453 | 44.00% |
| 002 | 12개월 | 2126.306 | 1189.108 | 44.08% |
| 002 | 전체 | 2398.093 | 1404.128 | 41.45% |
| 005 | 1개월 | 404.575 | 201.954 | 50.08% |
| 005 | 6개월 | 1620.354 | 1075.564 | 33.62% |
| 005 | 12개월 | 2888.563 | 1855.894 | 35.75% |
| 005 | 전체 | 3142.823 | 2071.278 | 34.09% |

기간은 시작 포함·종료 제외입니다. 1개월은 2026-08-01~2026-09-01,
6개월은 2026-03-01~2026-09-01, 12개월은 2025-09-01~2026-09-01,
전체는 2025-10-01~2026-11-01입니다.
12개월은 달력 범위이며 당시 실제 사용량 기록 월은 11개였습니다.

모든 측정 범위에서 최종 SQL의 시간이 짧았고 전체 기간 성능 저하도 없었습니다.
이 자료는 워밍업 후 DB 실행시간의 개선입니다. API·n8n·네트워크 응답시간이나
모든 반환 값의 동등성, Lambda·workflow 배포 완료 여부를 함께 증명하지 않습니다.

## 재현과 검증

실행 방법과 입력은 [비교 도구 안내](../../tools/query-plans/README.md)에 있습니다.

```psql
\set plan_month 2026-08-01
\set reader_plan_repeats 5
\i C:/kt_nd/tools/query-plans/compare_operations_reader_preagg.psql

\set plan_start_date 2026-03-01
\set plan_end_date_exclusive 2026-09-01
\set plan_analyze true
\i C:/kt_nd/tools/query-plans/explain_operations_preagg.psql
```

뷰의 컬럼 계약·중복·월 합계·권한·월 키는
[집계 품질 SQL](../../db/quality/operations/ai/030_monthly_preagg_quality.sql)로 별도 확인합니다.
권한·컬럼 계약 검사는 파이프라인의 [조회 권한 검사](../../db/quality/030_reader_permissions.sql)에 포함됩니다.
전체 원문과 미채택 실험은 로컬 `tmp/unused/`에 보관하며 Git 대상에 포함하지 않습니다.

이번 정리에서는 최종 SQL과 카탈로그 본문의 일치, SQL include 경로, 문서 링크와
보관 파일의 해시를 확인했습니다. 로컬 PostgreSQL 설치에 `postgres.bki`가 없어
폐기용 DB를 구성하지 못했으므로 새 상세 계획 도구의 실제 DB 실행 검증은 남아 있습니다.

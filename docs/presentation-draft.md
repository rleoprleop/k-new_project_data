발표에서 바로 읽거나 이후 PPT로 나눌 수 있도록, **프로젝트 배경부터 데이터 생성, 구조 설계, 기술 선택, 실제 수정 이슈, 활용 시나리오까지 연결한 상세 초안**으로 작성했습니다.

현재 저장소의 코드·문서·커밋 이력을 기준으로 정리했습니다. 설계 이유는 구현과 문서에서 읽히는 의도를 발표용 문장으로 풀어 썼습니다. 실제 AWS 처리 시간, 최종 적재 건수, 추천 정확도처럼 실행 결과가 필요한 수치는 임의로 넣지 않았습니다. 최근 작업 중인 뷰 스키마 명세와 고객 선정 도구도 포함했습니다.

**발표 제목 초안: 통신 데이터 기반 개인화 추천 및 운영 분석을 위한 데이터 파이프라인 구축**

**1. 프로젝트의 배경과 해결하려던 문제**

이번 프로젝트에서는 통신 고객의 요금제, 데이터 사용량, 선택 혜택, 가족결합 정보를 함께 분석할 수 있는 데이터 파이프라인을 구축했습니다.

처음에 생각한 문제는 고객이 현재 이용 중인 요금제와 실제 이용 패턴이 반드시 일치하지는 않는다는 점이었습니다. 데이터 사용량이 많은데 기본 제공량이 적은 요금제를 사용하는 고객도 있고, 반대로 사용량은 적은데 고가 요금제를 유지하는 고객도 있을 수 있습니다. 또한 특정 콘텐츠를 많이 이용하면서도 관련 혜택을 선택하지 않았거나, 가족결합 조건을 충족하면서 결합 할인에 가입하지 않은 고객도 있을 수 있습니다.

이런 상황을 판단하려면 월 데이터 사용량 하나만으로는 부족합니다. 현재 요금제의 월정액과 제공량, 콘텐츠별 사용 비중, 선택한 부가서비스, 가족 구성, 인터넷 보유 여부, 할인 정책을 함께 확인해야 합니다.

운영 관점에서도 같은 데이터가 필요합니다. 다만 운영 담당자가 알고 싶은 것은 특정 고객의 추천 결과보다는 전체 가입자의 요금제 분포, 연령대별 콘텐츠 이용 차이, 가족결합 가입 현황, 사용량 급증 고객 같은 내용입니다.

따라서 프로젝트의 목표를 두 가지로 나누었습니다. 하나는 고객별 요금제와 혜택을 검토하기 위한 개인화 분석이고, 다른 하나는 전체 고객과 상품 이용 현황을 파악하기 위한 운영 분석입니다.

이를 위해 원본 데이터를 생성하는 단계부터, 데이터를 목적에 맞게 가공하고 검증하는 단계, 외부 AI가 정해진 방식으로 조회할 수 있도록 제공하는 단계까지 연결했습니다.

**2. 제가 구현한 작업의 전체 범위**

작업 범위는 크게 여섯 부분으로 구성했습니다.

첫 번째는 합성 통신 데이터 생성기입니다. 고객, 가족, 요금제, 혜택, 할인 정책, 콘텐츠 사용량을 서로 연결되는 데이터로 생성하도록 만들었습니다.

두 번째는 PostgreSQL 데이터 모델입니다. 원본 CSV를 임시 적재한 뒤 운영과 개인화 목적에 맞는 DW와 DM을 구성했습니다.

세 번째는 배치 실행 파이프라인입니다. 전체 데이터를 한 번에 적재하는 방식뿐 아니라, 고객·정책 기준 데이터를 먼저 준비한 뒤 사용량을 날짜별로 추가하는 증분 방식과 이미 적재된 날짜를 수정하는 정정 방식을 구현했습니다.

네 번째는 데이터 품질 검사와 실행 이력 관리입니다. 단순히 SQL 실행이 끝났는지를 보는 대신, 원본 관계와 변환 결과의 사용량 합계가 맞는지 검사하고 성공한 날짜를 기록하도록 했습니다.

다섯 번째는 AWS 실행 환경입니다. 로컬 파이프라인을 Lambda 컨테이너에서 재사용할 수 있도록 S3, Secrets Manager, PostgreSQL 접속과 연결했습니다.

여섯 번째는 분석과 시연을 위한 조회 도구입니다. 운영·개인화 고정 쿼리 카탈로그, AI 조회 뷰, 뷰 스키마 명세, 추천 사례 고객을 선정하는 SQL을 정리했습니다.

현재 구현의 중심은 추천 판단에 사용할 데이터를 안정적으로 제공하는 기반입니다. 추천 판단과 설명은 외부 AI·n8n 워크플로에서 수행하도록 경계를 정했습니다.

**3. 실제 고객 데이터 대신 합성 데이터를 사용한 이유**

이 프로젝트에서는 실제 고객 정보나 실제 청구 데이터를 사용하지 않았습니다. 고객 이름과 사용 이력도 모두 합성 데이터입니다.

합성 데이터를 사용한 이유는 개인정보 없이 데이터 처리 구조를 검증할 수 있고, 추천에 필요한 다양한 상황을 의도적으로 만들 수 있기 때문입니다.

일반적인 고객만 생성하면 추천 시연에서 보여 줄 문제가 충분히 나타나지 않을 수 있습니다. 따라서 사용량에 비해 요금제가 부족한 고객, 사용량에 비해 요금제가 비싼 고객, 콘텐츠 이용과 선택 혜택이 맞지 않는 고객을 생성 규칙에 포함했습니다.

또한 같은 조건으로 데이터를 다시 만들 수 있어야 오류를 재현하고 수정 결과를 비교하기 쉽습니다. 이를 위해 난수 시드와 기준일을 고정할 수 있도록 구성했습니다.

기본 생성 설정은 사용자 1,000명, 사용 기간 90일, 난수 시드 3, 의도적 비최적 요금제 비율 20%입니다. 기본 기준일은 `2026-09-15`이며, 실행 옵션으로 사용자 수·기간·기준일을 변경할 수 있습니다.

여기서 20%는 실제 통신 고객의 비최적 요금제 비율을 의미하지 않습니다. 추천과 이상 사례 검토를 위해 설정한 합성 데이터 생성 조건입니다. 가족 비율이나 직업별 사용 성향 등도 실제 고객 통계와 구분해 설명하도록 문서화했습니다.

생성 규칙의 근거와 합성 가정은 [데이터 생성 상세 사양](C:/kt_nd/docs/data/generation-spec.md)에 정리했습니다.

**4. 합성 데이터를 단순 무작위로 만들지 않은 이유**

고객 나이, 요금제, 가족 여부, 사용량을 각각 독립적인 난수로 생성하면 데이터 간 관계가 부자연스러워질 수 있습니다.

예를 들어 부모와 자녀의 나이가 거의 같거나, 어린 고객이 일반적인 성인 지출 성향을 가지거나, 가족결합에 필요한 인터넷 회선이 없는데 할인 혜택을 받는 상황이 만들어질 수 있습니다.

그래서 데이터 생성에서는 각 정보가 다음 단계에 영향을 주도록 순서를 설계했습니다.

먼저 정책과 상품 마스터를 만들고, 가족 구조와 독립 사용자를 생성합니다. 이후 고객의 연령과 내부 직업 정보를 바탕으로 지출 성향과 사용량 프로필을 설정합니다. 이 정보를 이용해 현재 요금제를 배정하고, 선택 서비스와 가족결합 상태를 생성한 다음, 최종적으로 일별 콘텐츠 사용량을 만듭니다.

연령 분포는 문서에 정의한 인구 분포를 바탕으로 하되, 전체 인구 분포와 이동통신 가입자의 분포가 같다고 보지 않았습니다. 어린 연령과 고령 연령에는 가입 보정값을 적용했습니다.

가족 구조도 단일 형태로 만들지 않았습니다. 부부, 부모와 자녀, 형제자매, 한부모, 3세대 등 여러 유형을 사용했습니다. 부모와 자녀는 최소 18세, 조부모와 손자녀는 최소 36세의 연령 차이가 성립하도록 검증했습니다.

직업은 최종 고객 CSV에는 저장하지 않습니다. 대신 데이터 생성 내부에서 요금제 지출 성향과 콘텐츠 이용 패턴에 영향을 주는 변수로 사용했습니다. 최종 분석에 필요하지 않은 내부 변수는 출력에서 제외한 것입니다.

**5. 데이터 사용량을 생성한 방식과 그 이유**

데이터 사용량은 모든 고객에게 같은 평균과 같은 변동을 적용하지 않았습니다.

사용자를 초저사용, 저사용, 일반 사용, 고사용, 초고사용 프로필로 나누고 연령과 내부 직업에 따라 선택 확률을 다르게 설정했습니다. 예를 들어 젊은 연령에서는 높은 사용량 프로필의 비중을 높이고, 고령 연령에서는 낮은 사용량 프로필의 비중을 높였습니다.

일별 사용량에는 감마분포를 사용했습니다. 사용량이 음수가 될 수 없고, 평균보다 많이 사용하는 날이 나타날 수 있는 형태를 만들기 위한 선택입니다. 여기에 주말 사용량 증가와 사용자별 로그정규 노이즈를 적용했습니다.

기본 일별 사용량만 생성하면 유한 데이터 요금제와 무제한 요금제의 차이가 충분히 드러나지 않습니다. 그래서 유한 데이터 요금제에는 월 누적 소진율을 반영했습니다.

사용자가 제공량을 많이 소진하면 관찰, 절약, 임계, 소진 단계로 이동하고, 단계에 따라 총사용량과 콘텐츠 비중이 달라지도록 했습니다. 영상과 숏폼 사용 비중은 줄어들고, 상대적으로 메신저나 웹의 비중은 높아질 수 있도록 구성했습니다.

이월 요금제는 직전 월의 잔여량을 다음 달 사용 가능량에 반영했습니다. 출력 기간이 월 중간에 시작하더라도 월 누적량이 갑자기 0에서 시작하지 않도록, 이전 기간을 내부적으로 먼저 계산하는 준비 구간도 두었습니다.

이 과정에서 중요하게 본 점은 관측 사용량과 잠재 수요가 다를 수 있다는 것입니다. 데이터가 부족해서 사용을 줄인 고객은 실제 사용량만 보면 적게 사용하는 고객처럼 보일 수 있습니다. 따라서 합성 데이터에서도 요금제 제약이 사용량에 영향을 주는 상황을 표현했습니다.

이후 일별 총사용량을 영상, 숏폼, 음악, AI, 전자책, 웹, SNS, 메신저 등 13개 콘텐츠 대분류에 배분했습니다. 일부 대분류는 YouTube 영상, YouTube Shorts, YouTube Music, Netflix 등 제한적인 상세분류로 한 번 더 나누었습니다.

상세분류는 선택 혜택과 실제 사용 패턴을 연결하는 데 필요한 수준으로 유지했습니다. 검색어, 영상 제목, 세션 정보 같은 세부 활동 데이터는 저장하지 않았습니다.

마지막으로 소수점 반올림 때문에 콘텐츠별 합계와 일별 총사용량이 달라지는 문제가 없도록 잔차를 보정했습니다. **일별 총사용량과 콘텐츠별 사용량 합계가 정확히 일치하는 것**을 생성 단계의 검증 기준으로 삼았습니다.

**6. 요금제와 혜택을 배정한 방식**

요금제는 단순히 전체 상품 중 하나를 무작위로 고르지 않았습니다.

사용자의 월 데이터 필요량, 지출 성향, 연령별 추가 데이터 혜택, 콘텐츠 성향, 가족 여부 등을 바탕으로 요금제별 적합도 점수를 계산했습니다.

예를 들어 데이터 필요량이 높은 고객에게는 무제한 요금제의 점수가 높아지고, 사용량이 매우 적은 고객에게는 고가 무제한 요금제의 점수가 낮아지도록 했습니다. 연령 혜택이 적용되는 고객은 기본 제공량뿐 아니라 추가 제공량도 고려했습니다.

계산한 점수는 softmax를 통해 선택 확률로 변환했습니다. 조건이 비슷한 고객이 모두 같은 요금제를 이용하는 데이터가 만들어지지 않도록 하기 위해서입니다.

동시에 기본적으로 고객의 20%에는 비최적 사례를 의도적으로 넣었습니다.

| 생성 사례 | 표현하려는 상황 |
| --- | --- |
| 고사용량·낮은 제공량 요금제 | 현재 요금제의 데이터 제공량이 부족할 수 있는 고객 |
| 저사용량·고가 요금제 | 요금제 하향을 검토할 수 있는 고객 |
| 영상 이용·초이스 혜택 없음 | 콘텐츠 이용과 요금제 혜택이 맞지 않는 고객 |
| 초이스 혜택 저활용 | 선택한 혜택을 변경할 여지가 있는 고객 |

이 내부 사례 라벨은 생성과 검증에만 사용하고 최종 CSV에는 출력하지 않았습니다. 추천 분석에서는 라벨을 읽는 대신 실제 사용량과 현재 상품 상태를 근거로 상황을 찾아야 하기 때문입니다.

혜택 데이터에서는 **요금제가 제공할 수 있는 혜택과 고객이 실제로 선택한 혜택**을 분리했습니다.

`plan_benefits`는 선택 가능한 후보와 고정 혜택을 저장하고, `user_services`는 실제 고객의 선택을 저장합니다. 이 구조 덕분에 “현재 요금제에서 받을 수 있는데 선택하지 않은 혜택”과 “현재 요금제 자체에 없는 혜택”을 구분할 수 있습니다.

**7. 가족결합과 할인 정책을 별도로 모델링한 이유**

가족결합은 고객 한 명의 요금제만으로 판단할 수 없습니다.

가족 구성원의 모바일 요금제 합계, 고가 회선 수, 인터넷 보유 여부와 상태, 인터넷 상품 그룹, 약정기간, 베이스 회선 지정 등이 함께 영향을 줍니다.

따라서 가족 정보, 결합에 참여하는 구성 정보, 할인 정책, 고객이 실제로 받는 할인 종류를 분리했습니다.

가족은 `families`, 참여 구성은 `bundle_discount_compositions`, 할인 종류는 `discounts`, 세부 적용 조건은 할인 규칙 테이블에 저장했습니다. 고객별 적용 상태는 `user_discounts`로 연결했습니다.

이렇게 구성하면 고객의 현재 가입 상태와 정책상 가능한 상태를 비교할 수 있습니다.

특히 프리미엄 가족결합에서는 모든 고가 회선에 같은 할인이 적용되지 않습니다. 베이스 회선과 추가 고가 회선을 구분해야 하며, 인터넷 조건과 최소 고가 회선 수도 확인해야 합니다.

총액결합에서도 가족의 모바일 월정액 합계가 할인 구간을 결정합니다. 인터넷 상품 그룹과 약정기간은 정책표 선택 조건으로 사용하고, 인터넷 이용료를 모바일 월정액 합계에 더하지 않았습니다.

최종 CSV에는 예상 청구액이나 잠재 할인액을 고정된 정답으로 저장하지 않았습니다. 할인 종류와 적용 조건을 저장하고, 필요한 시나리오에서 정책표를 이용해 계산하도록 했습니다.

계산 결과와 입력 조건을 분리하면 요금제 변경이나 결합 방식 변경을 검토할 때 같은 정책 데이터를 다시 사용할 수 있다는 장점이 있습니다.

**8. 원본 데이터를 14개 논리 테이블로 구성한 이유**

원본 데이터는 총 14개 논리 테이블로 구성했습니다.

| 구분 | 테이블 |
| --- | --- |
| 고객·가족·결합 | `users`, `families`, `bundle_discount_compositions` |
| 요금제·연령 혜택 | `plans`, `age_benefits`, `plan_age_benefits` |
| 서비스·요금제 혜택 | `additional_services`, `plan_benefits` |
| 할인 정책 | `discounts`, `internet_bundle_discount_rules`, `premium_family_discount_rules` |
| 고객 적용 상태 | `user_discounts`, `user_services` |
| 콘텐츠 사용량 | `content_usage` |

고객 한 행에 모든 정보를 넣으면 서비스나 할인 개수에 따라 컬럼 구조가 복잡해지고, 상품 정책이 고객 수만큼 반복됩니다. 사용량까지 같은 테이블에 넣으면 고객 상태와 일별 이용 이력의 단위도 섞입니다.

그래서 고객, 정책, 적용 상태, 사용 이력을 관계에 따라 분리했습니다.

또한 변화 주기가 다른 데이터도 구분했습니다. 고객과 상품·정책 기준 데이터는 스냅샷 13개로 준비하고, 양이 많이 증가하는 콘텐츠 사용량은 날짜별로 처리할 수 있게 구성했습니다.

이 구분이 이후 증분 파이프라인의 기반이 되었습니다.

**9. 전체 데이터 아키텍처를 설계한 이유**

전체 구조는 다음과 같습니다.

```text
Python 합성 데이터 생성
          ↓
원본 CSV 저장
로컬 파일 / AWS S3
          ↓
배치 실행
임시 staging 적재 및 원본 품질 검사
          ↓
 ┌─────────────────────┬──────────────────────┐
 │ 운영 DW             │ 개인화 DW            │
 │ 가명 키·연령대      │ 고객 ID·합성 이름    │
 │ category 사용량     │ category/detail 사용량│
 │         ↓           │          ↓           │
 │ 운영 DM             │ 개인화 DM            │
 │ 현황·세그먼트 집계  │ 고객별 사용량·상태   │
 └─────────────────────┴──────────────────────┘
          ↓
변환 결과 품질 검사
          ↓
성공 배치 저장 및 워터마크 갱신
          ↓
영역별 AI 조회 View
          ↓
n8n 고정 쿼리 조회
          ↓
외부 AI 분석 및 설명
```

이 구조에서는 각 계층이 서로 다른 책임을 갖습니다.

원본 저장소는 입력 데이터를 보관합니다. staging은 CSV를 읽고 검사하는 작업 공간입니다. DW는 목적별 상세 데이터를 보관합니다. DM은 자주 사용하는 집계와 현재 상태를 제공합니다. AI View는 외부 조회에 공개할 데이터 범위를 정의합니다.

계층을 나눈 이유는 오류가 발생했을 때 원본 문제인지, 변환 문제인지, 집계 문제인지 구분하기 쉽고, 업무 규칙이 바뀌었을 때 수정할 위치도 명확해지기 때문입니다.

설계 기준은 [데이터 아키텍처 문서](C:/kt_nd/docs/architecture.md)에 정리했습니다.

**10. 운영과 개인화를 분리한 이유**

같은 원본을 사용하더라도 운영 분석과 개인화 분석은 필요한 정보 수준이 다릅니다.

운영 분석에서는 이름보다 요금제, 연령대, 콘텐츠 카테고리, 가족결합 상태가 중요합니다. 반면 개인화 분석에서는 특정 고객을 조회하고 현재 이용 상태를 설명해야 하므로 고객 ID와 이름, 상세 콘텐츠 사용량이 필요합니다.

이를 하나의 테이블과 하나의 조회 계정으로 처리하면 필요하지 않은 정보까지 공개하거나, 반대로 개인화에 필요한 정보를 충분히 제공하지 못할 수 있습니다.

그래서 하나의 PostgreSQL 데이터베이스 안에서 스키마를 분리했습니다.

| 항목 | 운영 영역 | 개인화 영역 |
| --- | --- | --- |
| 고객 식별자 | HMAC 기반 가명 키 | 원본 합성 고객 ID |
| 이름 | 저장하지 않음 | 합성 이름 유지 |
| 나이 | 연령대 | 나이 유지 |
| 사용량 상세 | category 단위 | category와 detail 유지 |
| 주요 목적 | 전체 현황·분포·이상 사례 분석 | 고객별 요금제·혜택 검토 |
| 조회 계정 | `n8n_operations` | `n8n_personalization` |

데이터베이스는 하나를 사용했습니다. 현재 프로젝트에서는 두 영역을 같은 배치에서 처리하고 품질도 함께 검증하므로, 스키마 분리를 통해 목적과 권한을 구분하면서 운영 복잡도를 관리하는 방식이 적절하다고 판단할 수 있습니다.

상품과 할인 정책처럼 개인정보가 없는 마스터는 두 DW에 각각 저장했습니다. 공통 적재 코드는 공유하지만 별도의 공통 DW 스키마를 만들지는 않았습니다. 각 영역의 조회 관계가 해당 영역 안에서 이어지도록 구성한 것입니다.

이 선택에는 마스터 데이터가 중복 저장되는 비용이 있지만, 두 영역의 구조와 권한을 이해하기 쉽다는 장점이 있습니다.

**11. 운영 영역에서 HMAC 가명화를 사용한 이유**

운영 데이터는 이름을 제거하더라도 고객별 사용량을 연결할 수 있어야 합니다.

고객 ID를 완전히 제거하면 같은 고객의 날짜별 사용량을 이어서 분석하기 어렵고, 매번 다른 난수로 바꾸면 신규 사용량을 기존 고객과 연결할 수 없습니다.

그래서 비밀 키를 사용하는 HMAC-SHA256 방식으로 가명 식별자를 생성했습니다. 같은 원본 ID와 같은 비밀 키를 사용하면 같은 가명 키가 나오므로, 고객별 사용량을 지속적으로 연결할 수 있습니다.

사용자, 가족, 결합 구성 등 식별자 종류별로 입력 도메인을 구분했습니다. 동일한 원본 문자열이 서로 다른 종류의 식별자에 나타나더라도 용도에 따라 다른 가명 키를 만들도록 한 것입니다.

운영 영역에서는 이름을 제외하고 나이를 연령대로 바꾸며, 콘텐츠 detail은 category로 합산했습니다. 식별자만 바꾸는 것과 함께 분석 목적에 필요한 정보 수준으로 데이터를 줄였습니다.

다만 이 데이터는 고객별 연결이 가능한 가명 데이터입니다. 발표에서 완전한 익명 데이터라고 표현하지 않는 것이 정확합니다.

또한 초기화와 이후 증분 적재에서 같은 HMAC 키를 유지해야 합니다. 키가 바뀌면 기존 고객과 신규 사용량의 연결 키도 달라질 수 있기 때문에, AWS에서는 Secrets Manager를 통해 안정된 키를 전달하도록 구성했습니다.

**12. 원본을 PostgreSQL에 영구 중복 저장하지 않은 이유**

구조를 정리하면서 원본 CSV를 영구 Landing 테이블에 계속 저장하는 방식에서, 배치 세션의 임시 staging에 적재하는 방식으로 변경했습니다.

현재 원본은 로컬 파일이나 S3에 있고, PostgreSQL에는 목적별 DW와 DM을 유지합니다.

임시 staging은 원본을 읽고 검사하는 동안만 존재하며 트랜잭션이 끝나면 삭제됩니다. 따라서 같은 원본을 파일 저장소와 영구 Landing 테이블 양쪽에 유지하는 부담을 줄일 수 있습니다.

그 대신 추적에 필요한 메타데이터는 `audit`에 남겼습니다. 어떤 파일을 읽었는지, 체크섬이 무엇인지, 몇 행을 읽었는지, 어떤 배치에서 처리했는지를 기록합니다.

이 구조는 원본 본문 보관과 처리 이력 보관을 구분한 것입니다. 데이터 재처리는 원본 파일을 기준으로 수행하고, 실행 확인은 감사 메타데이터를 기준으로 수행하도록 했습니다.

**13. DW와 DM을 나누고 Star Schema를 사용한 이유**

DW는 목적에 맞는 상세 데이터를 저장하고, DM은 실제 질문에 사용할 집계와 현재 상태를 제공합니다.

예를 들어 고객의 월 사용량을 물을 때마다 콘텐츠 상세 행 전체를 다시 합산하면 반복 작업이 많아집니다. 운영 분석에서도 요금제·연령대·카테고리별 사용량을 조회할 때마다 같은 조인과 집계를 수행해야 합니다.

그래서 DM에는 일별 총사용량, 월별 총사용량, 월별 콘텐츠 사용량, 현재 서비스와 할인 상태 등을 구성했습니다.

DM은 고객·요금제·날짜·콘텐츠 같은 Dimension과 사용량·현재 상태 데이터를 연결하는 Star Schema 형태로 설계했습니다.

여기서 중요한 것은 한 행이 의미하는 단위, 즉 grain을 명확히 정하는 것입니다.

운영의 일별 세그먼트 사용량은 “일자 × 현재 요금제 × 연령대 × 콘텐츠 카테고리” 단위입니다. 개인화의 일별 총사용량은 “고객 × 일자” 단위이고, 월별 상세 사용량은 “고객 × 월 × 콘텐츠 상세분류” 단위입니다.

이 단위를 명확히 해야 조인 후 사용량이나 고객 수가 중복되는 문제를 줄일 수 있습니다.

Star Schema라는 형태 자체가 속도를 보장하는 것은 아닙니다. 실제 조회 비용을 줄이는 요소는 자주 사용하는 일·월 집계를 미리 계산하는 것, 조회 조건에 맞는 인덱스를 두는 것, 조인 단위를 정확히 맞추는 것입니다.

개인화 일별 상세 사용량은 DM에 물리 테이블로 다시 복제하지 않고 DW 상세 데이터에 연결되는 View로 제공했습니다. 일·월 집계는 저장하되 대용량 상세 행의 중복 저장은 줄이는 방식입니다.

현재 구조는 현재 요금제를 기준으로 분석하며 요금제 변경 이력 스냅샷을 유지하지 않습니다. 따라서 과거 사용량을 조회하더라도 당시의 요금제 상태까지 재현하는 구조는 아니라는 범위를 분명히 했습니다.

DW·DM의 객체와 집계 기준은 [DB 구조 문서](C:/kt_nd/db/README.md)에 정리했습니다.

**14. 데이터가 커질 때를 고려해 생성 방식을 바꾼 이유**

콘텐츠 사용량은 고객 수와 날짜 수뿐 아니라 콘텐츠 상세분류 수에 비례해 증가합니다.

따라서 사용자 정보가 작더라도 콘텐츠 사용량은 빠르게 커질 수 있습니다. 전체 상세 사용량을 하나의 DataFrame으로 만든 뒤 저장하면 메모리 사용량이 커지는 문제가 발생할 수 있습니다.

이를 고려해 날짜별 파티션 출력과 스트리밍 생성 방식을 추가했습니다.

현재 생성기는 단일 파일, 날짜별 파일, 두 방식 동시 출력의 세 가지 구성을 지원합니다. 날짜별 파일은 다음과 같은 경로를 사용합니다.

```text
raw/content_usage/
  event_date=YYYY-MM-DD/
    part-000.csv
```

특히 `daily` 방식과 분석용 출력 생략 옵션을 함께 사용하면, 사용자 묶음별로 콘텐츠 사용량을 생성하고 날짜별 파일에 이어 씁니다. 기본 사용자 버퍼 크기는 100명이며 옵션으로 조절할 수 있습니다.

이 방식에서는 전체 콘텐츠 상세 데이터를 한꺼번에 메모리에 보관하지 않습니다. 동시에 기존 생성 규칙과 난수 순서를 유지하도록 설계해 출력 방식이 달라도 생성 논리가 달라지지 않게 했습니다.

이 개선은 데이터 규모 증가에 대응하기 위한 구현입니다. 실제 메모리 절감량이나 최대 처리 건수는 측정 결과를 확보한 뒤 성과 수치로 제시해야 합니다.

**15. 전체 배치와 증분·정정 모드를 나눈 이유**

처음부터 모든 데이터를 매번 다시 적재하는 방식만 사용하면 실행은 단순하지만 데이터가 커질수록 반복 비용이 증가합니다.

그래서 실행 모드를 네 가지로 나누었습니다.

| 모드 | 처리 내용 | 사용 목적 |
| --- | --- | --- |
| 전체 배치 | 스냅샷 13개와 전체 사용량 적재 | 전체 데이터 재구성 |
| 증분 초기화 | 사용량을 제외한 스냅샷 13개 적재 | 고객·상품·정책 기준 데이터 준비 |
| 신규 증분 | 날짜별 콘텐츠 사용량 추가 | 마지막 성공일 이후 적재 |
| 원본 정정 | 이미 적재한 날짜의 사용량 교체 | 변경된 원본 반영 |

증분 처리에서는 마지막으로 성공한 날짜를 워터마크로 저장합니다. 다음 적재는 워터마크 다음 날부터 시작해야 하며, 날짜가 누락되면 실패하도록 했습니다.

예를 들어 9월 10일까지 성공했다면 다음 처리는 9월 11일부터 시작해야 합니다. 9월 11일을 건너뛰고 9월 12일을 처리하면 데이터가 연속적으로 적재되었다는 전제가 깨지므로 허용하지 않습니다.

Lambda에서는 한국 시간 기준 오늘과 미래 날짜의 사용량 적재를 차단합니다. 신규 증분 요청은 1~7일 범위로 제한했습니다.

정정은 신규 적재와 구분했습니다. 이미 처리한 날짜의 원본이 달라졌다면 별도 `run_id` 경로에 수정 버전을 저장하고 해당 날짜를 교체합니다.

```text
event_date=YYYY-MM-DD/
  run_id=VERSION/
    part-000.csv
```

정정에서 특히 중요한 것은 집계 영향 범위입니다. 월 중간의 하루 사용량을 바꾸면 해당 날짜의 총사용량뿐 아니라 이후 날짜의 월 누적 사용량과 해당 월의 총합도 달라집니다.

따라서 정정 날짜의 DW 사용량을 교체한 후, 영향을 받는 일별 누적값과 월 집계를 다시 계산하도록 구현했습니다.

이 구조를 통해 “새로운 날짜를 추가하는 작업”과 “이미 처리한 날짜를 수정하는 작업”을 명시적으로 구분했습니다.

**16. 재실행과 동시 실행을 제어한 방식**

배치 파이프라인은 같은 요청이 다시 들어오거나 여러 실행이 겹칠 수 있다는 점을 고려해야 합니다.

먼저 원본 파일의 SHA-256 체크섬과 배치 입력을 이용해 소스 집합 체크섬을 계산하도록 했습니다. 초기화·증분·정정 SQL에서는 같은 체크섬으로 이미 성공한 입력을 다시 실행하면 추가 처리 없이 종료합니다.

다만 모든 실행 경로가 같은 동작을 하지는 않습니다. 전체 배치는 동일 입력이어도 전체 DW/DM을 다시 구성합니다. Lambda 신규 증분은 요청 범위가 이미 워터마크에 포함되면 `ALREADY_PROCESSED`를 반환합니다.

여기서 `ALREADY_PROCESSED`는 기존 날짜의 원본 파일 체크섬까지 다시 검증했다는 의미는 아닙니다. 기존 날짜의 원본 변경은 정정 경로로 처리하도록 했습니다.

동시 실행은 PostgreSQL advisory lock으로 제어했습니다. 전체 배치, 초기화, 증분·정정이 같은 `content_usage_daily` 잠금을 사용하므로, 서로 겹쳐 같은 DW/DM을 변경하지 않도록 구성했습니다.

또한 운영과 개인화 변환은 같은 데이터 배치 트랜잭션 안에서 실행합니다. 어느 한 영역의 변환이나 품질 검사가 실패하면 두 영역의 배치 데이터를 함께 롤백합니다.

이렇게 하면 운영에는 새 데이터가 반영됐지만 개인화에는 이전 데이터가 남는 상태를 줄일 수 있습니다.

스키마 DDL은 데이터 적재 트랜잭션보다 먼저 실행됩니다. 따라서 데이터 배치 실패와 스키마 변경의 유지 여부는 구분해서 설명해야 합니다.

실행과 재처리 규칙은 [파이프라인 문서](C:/kt_nd/pipeline/README.md)에 정리했습니다.

**17. 데이터 품질 검사를 파이프라인 안에 넣은 이유**

프로그램이 오류 없이 끝났다는 사실만으로 분석 데이터가 정확하다고 판단할 수는 없습니다.

고객과 요금제 연결이 잘못되었거나, 가입일 이전 사용량이 포함되었거나, 집계 과정에서 일부 데이터가 빠져도 SQL 자체는 실행될 수 있습니다.

그래서 품질 검사를 처리 단계에 포함했습니다.

생성 단계에서는 사용자·가족·상품·할인 간 관계, 가족 연령 조건, 서비스 선택 조건, 일별 총사용량과 콘텐츠 합계의 일치를 검사합니다.

저장된 CSV는 `check_distribution.py`로 다시 확인합니다. 내부 생성 과정만 보는 것과 실제 출력 파일을 검증하는 것을 분리한 것입니다.

staging에서는 고객이 참조하는 요금제와 가족이 존재하는지, 사용량의 고객 ID가 유효한지, 서비스와 할인 참조가 맞는지, 사용량이 음수가 아닌지 검사합니다.

DW에서는 원본에서 적재 대상인 행이 올바르게 반영됐는지 확인합니다. DM에서는 DW 사용량과 일·월 집계 합계가 일치하는지 확인합니다.

품질 규칙은 실패 행 수를 계산해 `audit.data_quality_result`에 기록하고, 실패 행이 있으면 예외를 발생시켜 데이터 배치를 중단하도록 했습니다.

변환 SQL과 품질 SQL의 폴더 구조도 맞췄습니다. 운영 DW 변환에는 운영 DW 검사가, 개인화 DM 변환에는 개인화 DM 검사가 대응하도록 배치했습니다. 업무 규칙을 바꿀 때 함께 수정해야 할 검증 위치가 보이도록 한 것입니다.

**18. 가입일 이전 사용량을 제외하도록 수정한 이슈**

데이터 업무 규칙에서 확인한 중요한 이슈는 가입일 이전의 사용량입니다.

합성 생성 기간과 고객 가입일을 조합하면 원본에 가입 이전 날짜의 사용량이 존재할 수 있습니다. 이를 그대로 분석 데이터에 넣으면 가입 전부터 서비스를 사용한 것처럼 해석됩니다.

이 문제를 해결하기 위해 운영과 개인화 DW 모두에서 다음 조건을 적용했습니다.

```sql
usage_date >= subscription_start_date
```

원본 CSV나 임시 staging의 행을 삭제하지는 않았습니다. 원본은 유지하고 DW 적재 대상에서 제외하도록 했습니다.

이 방식은 원본을 보존하면서 분석 대상의 업무 정의를 적용한다는 의미가 있습니다. 동시에 품질 검사도 전체 원본 합계가 아닌, 가입일 조건을 충족하는 원본 합계를 기준으로 비교하도록 수정했습니다.

이 때문에 S3 원본 행 수와 DW 행 수가 다를 수 있습니다. 운영 DW는 detail을 category로 집계하므로 개인화 DW와도 행 수가 다를 수 있습니다. 이런 차이는 적재 실패로 단정하지 않고 필터링과 집계 기준을 함께 확인해야 합니다.

현재 가입자는 `subscription_start_date <= 기준일`로 정의했고, 취소는 없는 합성 프로젝트 가정을 사용했습니다.

**19. AWS 배포에서 기존 파이프라인을 재사용한 이유**

로컬에서는 PowerShell 실행기가 파일과 설정을 준비하고, psql이 SQL 파이프라인을 실행합니다.

AWS에 배포할 때도 이 처리 로직을 유지했습니다. Python Lambda Handler는 이벤트 검증, S3 다운로드, 비밀 설정 조회, 기존 실행기 호출, 결과 확인을 담당합니다.

전체 호출 흐름은 다음과 같습니다.

```text
Lambda 이벤트
    ↓
Python Handler
    ↓
이벤트·날짜·기존 상태 검사
    ↓
S3 파일 다운로드 및 Secrets Manager 조회
    ↓
PowerShell 실행기
    ↓
psql 및 SQL 파이프라인
    ↓
audit 상태·품질·워터마크 확인
```

클라우드에서 별도의 적재·변환 로직을 다시 작성하면 로컬과 AWS의 동작이 달라질 가능성이 있습니다. 기존 파이프라인을 재사용하면 같은 SQL과 같은 배치 규칙을 두 환경에서 검증할 수 있습니다.

대신 Lambda에 필요한 도구를 컨테이너 이미지에 담았습니다. Python 런타임, PowerShell, PostgreSQL 클라이언트, 공개 RDS CA 인증서와 실제 파이프라인 코드가 포함됩니다.

생성기와 생성 CSV는 이미지에 포함하지 않았습니다. 원본 데이터는 S3에서 내려받으므로 데이터가 바뀔 때마다 이미지를 다시 빌드할 필요가 없도록 한 것입니다.

S3 원본 다운로드와 런타임 파일은 `/tmp`를 사용하며, 다운로드 전에 임시 저장 공간도 확인하도록 구현했습니다.

AWS에서는 한 Lambda가 운영과 개인화를 함께 처리합니다. 두 영역이 같은 워터마크와 배치 트랜잭션을 공유하므로 실행 상태를 한 경로에서 관리할 수 있습니다.

배포 구현은 [배포 모듈 문서](C:/kt_nd/deploy/README.md)와 [Lambda Handler](C:/kt_nd/deploy/lambda/handler.py)에 있습니다.

**20. 컨테이너 배포 과정에서 해결한 실행 환경 이슈**

배포에서는 데이터 로직 외에도 컨테이너 실행 환경과 관련된 수정이 있었습니다. 9월 30일 커밋 이력에서 확인되는 대표적인 내용은 다음과 같습니다.

첫 번째는 OpenSSL 패키지 충돌입니다. Dockerfile에서 명시적으로 설치하던 `openssl-libs` 항목을 제거하는 수정이 이루어졌습니다. 이 사례는 실행 도구를 추가할 때 베이스 이미지에 포함된 패키지와의 관계도 확인해야 한다는 점을 보여 줍니다.

두 번째는 PowerShell의 쓰기 경로입니다. Lambda 컨테이너에서는 애플리케이션의 쓰기 가능한 영역이 제한됩니다. PowerShell 실행에 필요한 캐시와 설정 경로를 기본 위치에 두면 해당 환경과 맞지 않을 수 있습니다.

이를 해결하기 위해 캐시·설정·데이터 경로와 모듈 분석 캐시를 `/tmp`로 지정했습니다.

세 번째는 컨테이너 진단 단계 보강입니다. 이미지가 빌드된다는 사실만으로 Lambda와 비슷한 제약에서 실행된다고 볼 수 없기 때문에, GitHub Actions에 다음 조건의 실행 검사를 추가했습니다.

- 네트워크 차단
- 읽기 전용 파일시스템
- 비관리자 사용자
- `/tmp`에만 쓰기 허용

이 환경에서 PowerShell 시작, 한국 시간대 조회, SQL 진입점 경로 해석, Handler의 `health` 동작을 확인하도록 구성했습니다.

이 작업을 통해 “이미지를 만들 수 있는가”와 “제약된 실행 환경에서 실제 도구가 시작되는가”를 별도로 검증했습니다.

**21. PostgreSQL CSV 적재 경로 문제를 해결한 과정**

CSV 적재 과정에서는 psql의 `\copy` 동작 때문에 경로 처리를 수정했습니다.

일반 SQL에서 사용하는 변수 치환 방식과 `\copy`의 처리 방식은 같지 않습니다. 파일 경로를 변수로 전달했다고 해서 `\copy` 안에서 기대한 대로 치환되는 것은 아니었습니다.

또한 로컬 실행 위치와 Lambda에서 다운로드한 임시 파일 위치가 다르므로, 현재 작업 폴더에 의존하는 경로는 실행 환경에 따라 달라질 수 있습니다.

수정 방식은 실행기가 CSV 입력 폴더를 절대 경로로 계산하고 `input_csv_directory`로 전달하는 것입니다. 적재 SQL은 `\cd`로 클라이언트 작업 폴더를 지정한 뒤 고정 파일명을 `\copy`에 사용합니다.

예를 들면 다음과 같은 구조입니다.

```text
실행기가 입력 폴더의 절대 경로 전달
    ↓
psql에서 해당 폴더로 이동
    ↓
users.csv, plans.csv 등의 고정 파일명으로 적재
```

SQL 파일 간 참조는 `\ir`를 사용해 해당 SQL 파일 위치를 기준으로 유지했습니다. CSV를 읽는 위치와 SQL을 참조하는 위치를 각각의 규칙에 맞게 처리한 것입니다.

감사 기록에는 원래의 절대 입력 경로를 유지했습니다. 실행을 위한 경로 처리와 원본 추적 정보를 함께 보존하도록 한 것입니다.

이 수정은 전체 배치, 증분 초기화, 증분 실행기에 반영했습니다.

**22. 연령 상한의 NULL 의미와 스키마 제약이 충돌한 이슈**

연령 혜택에는 상한이 없는 구간이 있습니다. 이런 경우 `max_age`의 NULL은 값이 빠진 오류가 아니라 “연령 상한 없음”이라는 의미입니다.

하지만 기존 DW 컬럼의 NOT NULL 제약은 이 원본 표현을 허용하지 않았습니다.

이 문제는 원본의 빈 값을 임의의 큰 숫자로 바꾸는 방식으로 처리하지 않았습니다. 그런 방식은 데이터의 의미를 바꾸고, 어디까지가 실제 정책인지 구분하기 어렵게 만듭니다.

대신 새로운 마이그레이션 파일을 추가해 운영과 개인화 DW의 `age_benefits.max_age`에서 NOT NULL 제약만 제거했습니다.

이 마이그레이션은 행 삭제나 타입 변경 없이 상한 NULL을 허용하며, 이미 적용된 상태에서도 재실행할 수 있습니다. 기존 DB에도 적용되어야 하므로 최초 생성 DDL 수정만으로 끝내지 않고 별도 번호의 변경 파일을 둔 것입니다.

품질 규칙에서는 상한이 존재하면 하한 이상이어야 한다는 조건을 검사하고, DW 적재 후에도 원본 NULL이 보존됐는지 확인하도록 했습니다.

이 사례에서는 빈 값의 기술적 처리보다 **그 값이 업무적으로 어떤 의미인지 먼저 정하는 것**이 중요했습니다.

관련 변경은 [연령 상한 마이그레이션](C:/kt_nd/db/schema/070_allow_open_ended_age_benefits.sql)에 있습니다.

**23. 정수 연령이 `18.0`으로 출력되어 발생한 타입 이슈**

프리미엄 가족결합 정책의 연령 컬럼에서는 다른 종류의 타입 문제가 있었습니다.

원본 데이터에 결측값이 섞여 있으면 pandas에서 정수처럼 보이는 컬럼도 소수 형태로 출력될 수 있습니다. 예를 들어 연령이 `18` 대신 `18.0`으로 저장될 수 있습니다.

이 값은 업무적으로는 정수이지만 PostgreSQL의 integer 컬럼에 CSV로 직접 적재하는 과정에서는 문제가 될 수 있습니다.

이를 해결하기 위해 임시 staging에서는 해당 연령 컬럼을 정밀도 제한 없는 `numeric`으로 읽도록 했습니다.

이후 품질 검사에서 값이 정확한 정수인지, integer 범위 안에 있는지 확인한 뒤 DW의 integer로 변환했습니다. NULL은 그대로 유지했습니다.

이 방식에서는 `18.0`은 허용할 수 있지만 `18.5`를 임의로 반올림해서 19로 적재하지는 않습니다. 원본이 의미하는 정수 표기 차이와 실제로 잘못된 소수 값을 구분한 것입니다.

검증 없이 정수 변환만 하면 잘못된 정책 값이 정상처럼 들어갈 수 있습니다. 그래서 읽기 → 검증 → 변환의 순서를 명시했습니다.

**24. 보안을 유지하면서 DB 연결 오류를 진단하도록 개선한 과정**

AWS에서 DB 연결이 실패하면 인증, DNS, 네트워크, TLS, 데이터베이스 이름 등 여러 원인이 있을 수 있습니다.

오류 출력을 그대로 로그에 남기면 원인을 찾기 쉽지만, 연결 정보나 원본 데이터가 포함될 수 있습니다. 반대로 원문을 모두 숨기고 “실패”만 표시하면 원인을 구분하기 어렵습니다.

그래서 원문을 외부로 출력하지 않으면서 고정된 진단 코드를 반환하도록 개선했습니다.

예를 들어 인증 실패는 `DB_AUTH_FAILED`, DNS 문제는 `DB_DNS_FAILED`, 연결 시간 초과는 `DB_CONNECT_TIMEOUT`, TLS 인증서 문제는 해당 TLS 진단 코드로 구분합니다.

psql의 종료 코드도 함께 확인해 연결 오류와 SQL 오류를 구분했습니다. SQL 데이터에 포함된 문자열을 연결 오류로 잘못 해석하지 않도록 한 것입니다.

Handler 응답에는 이벤트 검증, 설정 조회, 비밀 조회, DB 사전 검사, S3 다운로드, 파이프라인 실행, audit 검증 중 어느 단계에서 실패했는지도 포함됩니다.

비밀번호와 HMAC 키는 Secrets Manager에서 조회해 실행 중 자식 프로세스 환경으로 전달하며, 명령 인자나 응답에 넣지 않도록 구성했습니다. DB 연결은 `verify-full` TLS 검증을 사용합니다.

타임아웃 발생 시 자식 프로세스 그룹을 종료하는 처리도 추가했습니다. 제한 시간 이후 하위 실행이 남는 상황을 제어하기 위한 것입니다.

**25. 이미지 빌드와 Lambda 배포를 구분한 이유**

GitHub Actions에서는 Handler 오프라인 테스트, 이미지 빌드, 컨테이너 실행 검사를 거친 뒤 main 브랜치에서 ECR로 이미지를 업로드하도록 구성했습니다.

AWS 인증은 OIDC 기반 역할 사용으로 구성했습니다.

워크플로 실행 조건도 조정했습니다. 문서나 조회 도구만 수정했을 때마다 Lambda 이미지가 다시 빌드되지 않도록, 이미지에 실제 영향을 주는 경로를 기준으로 실행하도록 했습니다.

이 과정에서 ECR 업로드와 Lambda 업데이트를 구분했습니다. ECR의 `latest` 태그가 바뀌어도 기존 Lambda 함수가 자동으로 새 이미지를 사용하는 것은 아닙니다. 새 이미지로 Lambda 배포를 갱신하는 단계가 필요합니다.

또한 이미지 빌드 성공, `health` 성공, DB 연결 성공, 데이터 적재 성공은 서로 다른 확인 항목입니다.

그래서 AWS 실행 절차를 `health → check → initialize → incremental` 순서로 나눴습니다. 도구 시작을 먼저 확인하고, 연결과 원본 존재를 확인한 뒤, 실제 적재를 실행하도록 구성했습니다.

Lambda는 짧은 날짜 범위부터 검증하도록 문서화했습니다. 배포 가이드의 초기 설정은 메모리 2GB, 임시 저장 공간 2GB, 제한 시간 15분이며, 처리 범위는 실제 소요 시간을 확인하면서 조정하도록 했습니다.

이 설정은 출발점입니다. 실제 데이터 규모에서 적절한 처리 범위는 실행 시간과 DB 부하를 측정해 판단해야 합니다.

**26. AI가 자유롭게 SQL을 생성하지 않도록 한 이유**

AI 분석을 연결할 때 중요한 결정은 SQL 실행 범위를 고정하는 것이었습니다.

이 프로젝트의 조회 계약에서는 AI가 SQL을 작성하거나 수정하지 않습니다. AI는 등록된 `query_id`와 해당 쿼리에 정의된 parameter만 반환합니다.

예를 들어 특정 고객의 월별 일 사용량을 조회하려면 다음과 같은 요청을 사용합니다.

```json
{
  "query_id": "PERS_002",
  "parameters": {
    "user_id": "U00001",
    "year_month": "2026-09"
  }
}
```

n8n은 쿼리 ID가 허용 목록에 있는지, parameter 이름·타입·범위가 맞는지 검사하고 내부에 등록된 SQL을 실행하도록 계약을 정했습니다.

이렇게 하면 AI가 질문을 해석하는 역할과 데이터베이스가 쿼리를 실행하는 역할을 구분할 수 있습니다. 어떤 질문에 어떤 조회가 사용됐는지도 추적하기 쉽습니다.

결과 행 수도 카탈로그의 `max_rows` 기준으로 제어하도록 했습니다.

현재 카탈로그에는 운영 쿼리 30개와 개인화 쿼리 15개가 등록되어 있습니다.

운영에서는 가입자 현황, 요금제 점유율, 일·월 사용량 추세, 연령대별 콘텐츠 비중, 상위 고객 사용량 집중도, 사용량 급증 후보 등을 조회할 수 있습니다.

개인화에서는 고객의 월 사용량, 일별 월 누적 사용량, 상세 콘텐츠 사용량, 최근 7일·30일 사용량, 현재 요금제·서비스·할인·가족 상태, 추천 후보 요금제 등을 조회할 수 있습니다.

현재 저장소에서 확인되는 것은 조회 뷰, 쿼리 카탈로그와 n8n 실행 계약입니다. 실제 n8n 워크플로의 배포·실행 완료 여부는 별도 실행 결과로 확인해야 합니다.

계약은 [n8n 고정 쿼리 문서](C:/kt_nd/docs/integration/n8n-fixed-query-contract.md)에 정리했습니다.

**27. AI 조회용 View와 전용 계정을 둔 이유**

고정 쿼리와 함께 DB 권한도 제한했습니다.

`n8n_operations`는 운영 AI View만 조회하고, `n8n_personalization`은 개인화 AI View만 조회하도록 구성했습니다. 기본 역할에는 DW/DM 테이블 직접 조회 권한과 쓰기 권한을 부여하지 않았습니다.

View는 외부에서 사용할 데이터 구조를 고정하는 인터페이스 역할을 합니다. 내부 테이블을 모두 공개하지 않고 필요한 컬럼과 조인 결과를 제공할 수 있습니다.

계정에는 읽기 전용 기본 설정과 30초 쿼리 제한도 적용했습니다.

개인화 사용자 단위 쿼리에는 `user_id`와 `name`을 함께 반환하도록 했습니다. 이름을 얻기 위해 별도 쿼리를 연쇄 실행할 필요가 없고, 동명이인이 있더라도 고객 ID를 기준으로 해석할 수 있도록 한 것입니다.

운영 View에는 이름과 원본 고객 ID를 노출하지 않습니다.

**28. 최근에 뷰 스키마 명세를 추가한 이유**

쿼리 카탈로그는 어떤 조회를 실행할 수 있는지 알려 주지만, 결과 컬럼의 의미까지 충분히 설명하지는 못합니다.

AI가 결과를 정확히 설명하려면 한 행의 단위, 사용량 단위, 날짜 의미, NULL 의미, 조인 키, 중복 합산 가능성 등을 알아야 합니다.

그래서 현재 작업본에는 AI 조회 뷰의 스키마 명세 CSV를 추가했습니다. 운영은 10개 View의 58개 컬럼, 개인화는 12개 View의 87개 컬럼을 설명합니다.

명세에는 뷰 설명, 행 단위, 컬럼 타입과 의미, 단위, NULL 해석, 원천 표현식, 조인 시 주의점, 집계 제한 등을 담았습니다.

예를 들어 카테고리별 고유 고객 수를 모두 더하면 여러 카테고리를 이용한 고객이 중복될 수 있습니다. 일별 월 누적 사용량을 날짜별로 합산하면 누적값을 반복해서 더하게 됩니다.

이런 문제는 컬럼 이름만으로 예방하기 어렵습니다. 따라서 쿼리 선택 정보와 결과 해석 정보를 함께 제공하도록 했습니다.

이 명세는 저장소 SQL을 기준으로 작성한 데이터 사전이며, 실제 배포 DB에서 조회한 메타데이터와는 구분합니다.

관련 내용은 [AI 조회 뷰 스키마 안내](C:/kt_nd/docs/integration/view-schemas/README.md)에 있습니다.

**29. 추천 시연을 위한 고객 선정 도구를 만든 이유**

발표에서는 구조를 설명하는 것과 함께 실제 데이터에서 어떤 사례를 찾을 수 있는지 보여 주는 것이 필요합니다.

그래서 다섯 가지 고객 선정 쿼리를 준비했습니다.

첫 번째는 YouTube 사용량이 많지만 관련 혜택을 선택하지 않은 고객입니다. 최근 30일 YouTube 관련 사용량이 20GB 이상이고 전체 사용량의 30% 이상인 고객 중 해당 서비스를 선택하지 않은 고객을 찾습니다.

여기서 YouTube 사용량은 영상, Shorts, Music에 해당하는 데이터 사용량입니다. 시청시간이나 외부 유료 구독 여부를 의미하지는 않습니다.

두 번째는 고사용량·저가 요금제 고객입니다. 최근 30일 사용량이 80GB 이상이고, 월정액이 61,000원 이하이며 기본 제공량이 30GB 이하인 고객을 찾습니다.

이는 상위 요금제 검토를 위한 사례 조건입니다. 연령 추가 데이터와 이월량 등을 모두 반영한 실제 초과 사용 판정은 아닙니다.

세 번째는 저사용량·고가 요금제 고객입니다. 최근 30일 사용량이 15GB 미만인데 월정액이 80,000원 이상인 고객을 찾아 하향 검토 사례로 사용합니다.

이때도 사용량 외 부가서비스와 할인 가치가 있으므로, 선정 결과만으로 즉시 요금제 변경을 확정하지는 않습니다.

네 번째는 프리미엄 가족결합 미가입 사례입니다. 인터넷 조건과 고가 회선 수 등을 충족하는 가족에서 베이스 후보를 먼저 선정하고, 추가 고가 회선 중 초이스 고객을 찾습니다.

다섯 번째는 총액결합 미가입 사례입니다. 가족의 모바일 월정액 합계와 인터넷 상품 그룹·약정기간을 정책표에 대입해, 모바일 할인 후보 금액이 양수인 가족의 고객을 찾습니다.

가족 할인액은 고객별 금액과 구분했습니다. 가족 전체 할인 풀이 각 고객 행에 반복될 수 있으므로 이를 고객별로 합산하면 중복 계산됩니다. 프리미엄과 일반 총액결합의 시나리오 금액도 그대로 더하지 않도록 설명했습니다.

사용량 기반 사례는 30일이 모두 관측된 고객만 포함하며, 관측되지 않은 날짜를 0으로 채우지 않습니다. 신규 고객의 짧은 관측 기간을 일반적인 저사용량으로 오해하지 않도록 한 것입니다.

현재 문서에는 고객 선정 SQL의 실제 DB 실행과 사례별 추출 건수가 아직 검증되지 않았다고 명시되어 있습니다. 발표 시연 전에는 대상 DB에서 결과를 확인해야 합니다.

도구와 해석 기준은 [조회·검증 도구 문서](C:/kt_nd/tools/README.md)에 정리했습니다.

**30. 한글 인코딩 문제를 고려한 최근 개선**

고객 선정 SQL에서는 Windows 콘솔 입력 인코딩과 psql의 `client_encoding`이 서로 다를 수 있다는 점도 고려했습니다.

UTF-8 파일, CP949 콘솔, psql 세션 인코딩이 맞지 않으면 한글 문자열이 깨지거나 UTF-8 바이트 오류가 발생할 수 있습니다.

현재 작업본의 개별 고객 선정 SQL과 일괄 실행 파일은 본문을 ASCII 문자로 구성하고, 한글 결과 문구는 PostgreSQL Unicode 이스케이프로 표현하도록 정리했습니다.

이를 통해 파일 본문을 UTF-8 또는 UHC 세션에서 읽을 때 한글 리터럴의 바이트 해석에 의존하는 부분을 줄였습니다.

일괄 실행 도구는 다섯 사례를 같은 읽기 전용 스냅샷에서 순서대로 조회하고, 오류가 발생하면 중단하도록 구성했습니다.

이 작업은 SQL 로직이 맞는 것과 사용자의 실제 콘솔에서 실행할 수 있는 것이 별개의 문제라는 점을 반영한 개선입니다.

**31. 적재 성공을 확인하는 기준을 정리한 이유**

운영 과정에서는 Lambda 호출 종료, 파이프라인 성공, 목표 날짜까지 적재 완료를 구분해야 합니다.

Lambda 로그에 실행 종료 기록이 있다는 사실만으로 DB 적재 성공을 확정할 수는 없습니다. 반대로 과거 실패 이력이 남아 있다는 이유만으로 현재 데이터가 실패했다고 판단할 수도 없습니다.

그래서 읽기 전용 검증 도구에서 세 가지를 함께 확인하도록 했습니다.

첫 번째는 요청한 배치가 `SUCCEEDED`인지입니다.

두 번째는 품질 검사 결과가 실제로 기록되어 있고 실패 행 수가 0인지입니다.

세 번째는 증분 워터마크가 의도한 종료일까지 도달했는지입니다.

품질 검사 기록이 하나도 없는 상태를 실패 행 0개라고 해석하면 안 됩니다. 또한 실패한 배치의 품질 기록은 롤백될 수 있으므로, 실패 결과가 없다는 사실만으로 성공을 판단하지 않도록 했습니다.

타임아웃 이후 `RUNNING` 상태가 남을 수 있다는 점도 문서화했습니다. DB 상태값만으로 Lambda가 현재 실행 중인지 판단하지 않고 CloudWatch 실행 로그와 함께 확인하도록 했습니다.

선택적으로 운영 DW, 개인화 DW, 운영 DM, 개인화 DM의 사용량 총합을 비교하는 기능도 마련했습니다. 전체 총합 비교는 조회 부하가 크기 때문에 기본 상태 확인과 구분했습니다.

총합 일치는 중요한 검증이지만, 그것만으로 날짜별·개별 행의 완전성을 모두 증명하는 것은 아니라는 범위도 설명했습니다.

**32. 기술별 역할과 선택 이유**

이 프로젝트에서 사용한 기술은 각 단계의 역할에 맞춰 배치했습니다.

| 기술 | 담당 역할 | 이 구조에서의 사용 이유 |
| --- | --- | --- |
| Python | 합성 데이터 생성, Lambda 연결 코드 | 확률 기반 생성과 파일·AWS 처리 구현 |
| NumPy | 난수와 확률분포 | 감마·로그정규·디리클레 등 생성 규칙 적용 |
| pandas | 테이블 구성, 관계 검증, CSV 출력 | 관계형 형태의 합성 데이터 처리 |
| Faker | 합성 한국어 이름 | 실제 이름 없이 시연 가능한 고객 정보 생성 |
| CSV | 원본 교환 형식 | 생성 결과 확인과 PostgreSQL 적재에 사용 |
| PostgreSQL | DW/DM, 집계, 품질 검사 | 관계·트랜잭션·SQL 분석을 한 실행 기반에서 관리 |
| PowerShell | 로컬·컨테이너 배치 실행 | 파일 준비와 기존 SQL 실행 절차 재사용 |
| psql | SQL 진입점과 CSV 적재 | SQL 파일 실행, 배치 변수 전달, 클라이언트 적재 |
| S3 | AWS 원본 저장소 | 스냅샷과 날짜별 사용량 파일 보관 |
| Lambda | 제한된 날짜 범위의 배치 실행 | 이벤트 기반 파이프라인 호출 |
| Docker·ECR | 실행 도구 패키징과 이미지 보관 | 로컬 파이프라인 도구를 AWS 실행 환경에 포함 |
| Secrets Manager | DB 인증과 HMAC 키 관리 | 비밀값을 코드·저장소에서 분리 |
| GitHub Actions | 테스트·빌드·이미지 업로드 | 실행 환경 검증 후 이미지 제공 |
| n8n | 고정 쿼리 실행 계약 | AI 요청을 검증된 조회로 연결 |

이 선택에는 비용과 제약도 있습니다. PowerShell을 재사용하면 로컬과 AWS 처리 규칙을 공유할 수 있지만 컨테이너에 추가 런타임이 필요합니다. DW와 DM을 나누면 조회 구조가 명확해지지만 집계 갱신 로직이 필요합니다. 운영과 개인화를 함께 처리하면 데이터 상태를 맞추기 쉽지만 실행 시간과 실패 범위를 공유합니다.

따라서 기술 선택은 각 도구의 장점뿐 아니라, 프로젝트에서 관리할 수 있는 복잡도와 필요한 검증 범위를 함께 고려한 것으로 설명할 수 있습니다.

- 고객·상품·혜택·가족·사용량이 연결되는 재현 가능한 합성 데이터 생성

동시에 현재 범위도 분명히 설명해야 합니다.

데이터는 합성 데이터이므로 실제 고객 분포와 동일하다고 주장할 수 없습니다. 현재 요금제 중심의 스냅샷 구조이므로 과거 요금제 변경 상태를 재현하지 않습니다. 가족의 상세 관계는 최종 출력에 없으므로 일부 법정대리인 조건의 재판정에는 추가 정보가 필요할 수 있습니다.

추천 결과를 저장하거나 추천 정확도를 평가하는 체계는 현재 데이터 파이프라인과 별도의 과제입니다. n8n의 실제 실행 결과, AWS 처리 시간, 최종 적재량은 확보한 증빙을 기준으로 추가해야 합니다.
